The Cheat Sheet

Data Sizes
1 KB = 1,000 bytes 1 MB = 1,000 KB 1 GB = 1,000 MB 1 TB = 1,000 GB 1 PB = 1,000 TB 1 EB = 1,000 PB
Number Sizes
1 K = 1,000 (3 zeros) 1 Million= 1,000,000 (6 zeros) 1 Billion= 10^9 (9 zeros) 1 Trillion=10^12 (12 zeros) 100M × 10 = 1 Billion ← memorise
Time (Rounded)
1 minute = 60 sec 1 hour = 3,600 → use 4,000 ★ 1 day = 86,400 → use 100,000 1 month = 2.5M sec 1 year = 30M sec 5 years = 1,825 days
Object Sizes
int32 / bool 4 bytes int64 / double8 bytes UUID (binary) 16 bytes UUID (string) 36 bytes Tweet / DB row~500 bytes Photo (comp.) ~1 MB 1 min video ~10 MB 1 hr video ~1 GB raw
⚡
Golden Rule: Round aggressively. 86,400 → 100,000. Your job is to get the right order of magnitude, not the exact answer. Interviewers care about your thinking process, not your arithmetic. Being off by 2× is fine — being off by 100× or having no answer at all is not.
02

Traffic Calculations

Traffic tells you how many requests per second hit your infrastructure. Always split reads and writes — they require completely different solutions.

1
Write QPS — How fast data comes IN
New posts, messages, uploads per second
Write QPS = (DAU × writes per user per day) ÷ 100,000
Example — Twitter: DAU = 100 Million Writers/day = 100M × 5% = 5 Million (not everyone posts) Writes/day = 5M × 1 tweet each Write QPS = 5,000,000 ÷ 100,000 = 50 QPS
Architecture signal
< 1K QPS → single DB handles writes easily
1K–10K QPS → consider write replicas or async buffering
> 10K QPS → sharding or NoSQL (Cassandra/DynamoDB) needed
> 100K QPS → queue-based ingestion (Kafka), never write direct to DB
2
Read QPS — How fast data goes OUT
Feed loads, searches, profile views, API responses per second
Read QPS = (DAU × reads per user per day) ÷ 100,000
Example — Twitter: DAU = 100 Million Reads/day = 100M × 10 refreshes = 1 Billion Read QPS = 1,000,000,000 ÷ 100,000 = 10,000 QPS
Architecture signal
< 1K QPS → single DB fine
1K–10K QPS → add Redis cache
> 10K QPS → cache mandatory, CDN for media
> 100K QPS → distributed cache cluster, edge caching
3
Read:Write Ratio — Which side dominates
Drives your entire architecture strategy — the most important single number
Ratio = Read QPS ÷ Write QPS
RatioSystemStrategy
1:1MessagingOptimize both equally, persistent connections
10:1E-commerceCache product catalog, CDN for images
100:1News feedHeavy Redis caching, pre-computed feeds
200:1TwitterEntire architecture read-optimised, fan-out on write
4
Concurrent Users — Active connections at once
Tells you thread pool size, connection pool, WebSocket server capacity
Concurrent users = DAU × avg session duration (sec) ÷ 86,400
Example — Twitter: DAU = 100 Million Avg session = 10 minutes = 600 seconds Concurrent users = 100M × 600 ÷ 86,400 = ~700,000 This means 700K simultaneous open connections → Each server handles ~10K connections → Need 700K ÷ 10K = 70 servers minimum
5
Fan-out — Write amplification on social graphs
Critical for Twitter, Instagram, Facebook. 1 write → N writes to follower feeds
Effective write QPS = base write QPS × avg followers per user
Example — Twitter celebrity posts a tweet: Base write QPS = 50 Avg followers = 200 Fan-out write QPS = 50 × 200 = 10,000 fan-out writes/sec BUT — Kylie Jenner has 380M followers: 1 tweet → 380M inbox writes in seconds → This is why Twitter uses hybrid fan-out → Celebrities: fan-out on read (pull at query time) → Regular users: fan-out on write (pre-push to feeds)
💡
Fan-out on Write: Push tweet to all followers' feed caches immediately. Fast reads. Expensive writes for celebrities.

Fan-out on Read: Store tweet once, merge at read time. Slow reads. Cheap writes. Stale feeds until next load.
03

Storage Calculations

Storage tells you how much disk you need. Always estimate media separately — it dominates everything else by 10–100×.

6
Storage Per Day — Disk burned daily
List every field, sum bytes, add 30% buffer
Storage/day = writes per day × bytes per item
How to estimate bytes per item (always list fields): tweet_id = 8 bytes (int64) user_id = 8 bytes text (280 chars)= 300 bytes (1 byte per ASCII char) timestamp = 8 bytes likes_count = 4 bytes (int32) retweet_count = 4 bytes is_reply, flags = 4 bytes ────────── = 336 bytes Round up 30%: = ~500 bytes (extra fields, indexes, overhead) 5M tweets/day × 500 bytes = 2.5 GB/day (text only)
Architecture signal
< 1 GB/day → single DB, no worries
1–100 GB/day → dedicated DB server, monitor growth
> 1 TB/day → distributed storage mandatory (S3, HDFS)
7
Storage Over N Years — Long-term capacity
Always plan 5 years. Interviewers always ask this.
Storage (N years) = storage/day × 365 × N
Twitter example: 500 GB/day × 365 × 5 = 912,500 GB = ~900 TB Don't forget replication factor! Actual disk = logical storage × 3 (3 copies for durability) = 900 TB × 3 = 2.7 PB actual disk needed
⚠️
Most people forget replication factor! Every byte you store is stored 3× in distributed systems (one primary + two replicas). Your logical storage × 3 = actual disk purchased. Always mention this — it signals real-world awareness.
8
Metadata vs Payload Split — Hot vs Cold storage
Never store media in your DB. Store the URL, serve from object storage.
Twitter media split: Text tweets = 2.5 GB/day → PostgreSQL / MySQL Media (images)= 500 GB/day → Amazon S3 / GCS Media (video) = TB/day → S3 + CDN What goes in DB (hot, fast queries): tweet_id, user_id, text, timestamp, media_url (50 bytes) What goes in S3 (cold, cheap storage): actual image/video binary Cost difference: DB storage ~$200/GB/month S3 storage ~$0.023/GB/month → 8,000× cheaper to use S3 for media
9
Compression Ratio — Actual bytes on disk
Text compresses beautifully. Video is already compressed — don't double count.
Compression ratios by data type: Plain text (tweets, posts) → 60–70% smaller with gzip JSON API responses → 70–80% smaller with gzip Images (already JPEG/WebP) → 5–10% smaller (already compressed) Video (already H.264/H.265) → 0% benefit Effective storage calculation: Raw storage = 2.5 GB/day text After compress = 2.5 × 0.3 = 0.75 GB/day For deduplication (Dropbox, Google Drive): Dedup ratio = 30–70% for typical file storage Users often upload same file (memes, docs) SHA-256 hash → detect and store only once

Bandwidth Calculations

Bandwidth tells you how many bytes per second flow through your network. Egress costs money — this drives CDN decisions.

10
Ingress Bandwidth — Data flowing IN
Uploads, writes, messages incoming to your system
Ingress BW = Write QPS × bytes per write
Twitter example: Text ingress: 50 QPS × 500 bytes = 25 KB/sec Image uploads: 5 images/sec × 1MB = 5 MB/sec Total ingress: ~5 MB/sec (trivially small vs egress)
11
Egress Bandwidth — Data flowing OUT
The big one. Downloads, feed loads, video streams — this is what costs money.
Egress BW = Read QPS × bytes per response
Twitter feed example: Read QPS = 10,000 Response size = 20 tweets × 500 bytes = 10,000 bytes Egress BW = 10,000 × 10,000 = 100 MB/sec What this costs on AWS (without CDN): 100 MB/sec × 86,400 sec/day = 8.6 TB/day egress 8.6 TB × $0.09/GB = $775/day = $23,000/month With CDN (95% offload): $23,000 × 5% = $1,150/month ← use CDN!
Architecture signal
< 1 MB/sec → single server handles egress fine
> 10 MB/sec → CDN strongly recommended
> 100 MB/sec → CDN mandatory, multi-region PoPs
> 1 TB/sec → massive CDN (YouTube/Netflix scale), peer caching
12
Internal (East-West) Bandwidth — Between your own services
Microservices multiply your bandwidth internally. Often ignored, always matters.
Each external request triggers multiple internal calls: External request → Twitter feed load → Auth service (verify JWT) → Timeline service (get tweet IDs) → User service (get user data) → Media service (get image URLs) → Recommendation service (suggested tweets) = 5 internal calls per 1 external request Internal BW = Egress BW × internal fan-out = 100 MB/sec × 5 = 500 MB/sec internal traffic → Internal network must be 10 Gbps minimum → Same-DC traffic is "free" but still has limits
13
CDN Offload Ratio — What actually hits your origin
The number that tells you what your servers really need to handle
Origin BW = total egress × (1 - CDN cache hit rate)
Twitter with CDN: Total egress BW = 100 MB/sec CDN hit rate = 95% Origin BW = 100 MB/sec × (1 - 0.95) = 5 MB/sec → Origin only needs to handle 5 MB/sec, not 100 MB/sec → This changes your server sizing by 20× Cache hit rate benchmarks: Static assets (JS/CSS/images) → 95–99% hit rate User-specific data → 0% (can't cache) Public feeds (explore page) → 70–90% hit rate
05

Cache & Server Calculations

14
Cache Size — RAM needed for Redis/Memcached
Pareto principle: 20% of data gets 80% of reads — cache only the hot 20%
Cache size = hot items count × bytes per item Hot items = total items × 0.20 (Pareto)
Twitter example: Tweets today = 5M new tweets Hot 20% = 1M hot tweets Bytes each = 500 bytes Cache size = 1,000,000 × 500 = 500 MB Single Redis instance handles this (up to ~100GB RAM) For historical tweets feed: add user feed caches User feed cache = 100M users × top 100 tweet IDs × 8 bytes = 100M × 800 bytes = 80 GB → Redis Cluster with 3–4 nodes
15
Cache Hit Rate Impact — The real number that matters
Effective DB QPS is what your cache hit rate doesn't handle
Effective DB read QPS = Read QPS × (1 - cache hit rate)
Why this matters more than raw read QPS: Read QPS = 10,000 Cache hit rate = 95% DB read QPS = 10,000 × 0.05 = 500 QPS → Single MySQL handles 500 QPS easily! → Without cache: 10,000 QPS → DB explodes Cache hit rate targets: Twitter feed → aim for 95%+ (same tweets read many times) User profile → 80–90% (profiles change rarely) E-commerce cart → 0% (unique per user, can't cache)
16
TTL — How long to cache data
Too long = stale data shown. Too short = cache provides no benefit.
TTL by data type (how stale can it be?): Static config / feature flags → 24 hours User profile / avatar → 5–15 minutes Tweet / post content → 60 seconds (likes change) Live seat availability → 0–5 seconds (must be fresh) Trending hashtags → 30 seconds Search results → 2–5 minutes Exchange rates / prices → 1 second Add ±20% jitter to TTL to prevent thundering herd: TTL = base_ttl × (1 + random(-0.2, 0.2)) → Not all cache entries expire at same time
17
Server Count — How many app servers you need
Always add 2× headroom. Servers fail. Traffic spikes.
Servers = Peak QPS ÷ QPS per server × 2
QPS per server (rough estimates): API server (CPU-bound) = 5K–10K QPS API server (I/O-bound) = 20K–50K QPS Static file server = 100K+ QPS Redis (single instance) = 100K–1M QPS MySQL single node = 5K–10K QPS Example — Twitter: Peak read QPS = 30,000 (3× average 10K) QPS per server = 10,000 Servers needed = (30,000 ÷ 10,000) × 2 = 6 servers
18
DB Connection Pool — The silent killer nobody mentions
Runs out before QPS does. Causes mysterious production outages.
How connection exhaustion happens: App servers = 10 servers Threads per server = 50 threads Total DB connections= 10 × 50 = 500 connections to DB PostgreSQL default max_connections = 100 → 500 > 100 → DB refuses connections → 500 errors! Solutions: PgBouncer = connection pooler, 500 app → 20 real DB connections RDS Proxy = AWS managed pooler HikariCP = Java connection pool library Safe formula: app connections ≤ DB max_connections × 0.8 Always mention this in interviews → instant senior signal
19
DB Shard Count — When one DB isn't enough
Plan your sharding strategy before you need it
Shard count = total storage ÷ max per shard
Twitter example: 5yr storage = 900 TB Max per shard = 1 TB (beyond this, queries slow dramatically) Shards needed = 900 ÷ 1 = 900 shards → Consistent hashing to distribute users across shards → user_id % 900 = which shard to write to → Need to plan for rebalancing as data grows QPS-based sharding threshold: MySQL = maxes at ~10K QPS → shard when approaching this Mongo = maxes at ~30K QPS per node Cassandra = designed for horizontal sharding from day one

Advanced Calculations (Senior Rounds)

20
Latency Budget — Break your SLA into components
Forces you to justify every layer. If numbers don't fit, architecture must change.
Example — 100ms SLA breakdown: DNS lookup = 5ms (cached after first request) TCP handshake = 5ms (same DC) / 80ms (India→US) TLS 1.3 handshake = 5ms (TLS 1.2 = 10ms) Network (client → server) = 10ms Load balancer = 2ms App server processing = 15ms Cache lookup (Redis) = 1ms (in-memory, same DC) DB query (cache miss) = 10ms Network (server → client) = 10ms Browser render = 20ms ───────────────────────────────── Total = 83ms ✓ within 100ms SLA If DB needs 50ms → doesn't fit → must cache → cache mandatory If users are in India → +160ms RTT → must use edge/CDN
21
Replication Lag Tolerance — Consistency model choice
How stale can reads be? Drives your entire DB and consistency architecture.
Tolerance by system type: 0ms (Zero tolerance) → Payment, inventory, seat booking → Synchronous replication → PostgreSQL with synchronous_commit=on → Higher latency, never stale 100–500ms → Social feed, messaging read receipts → Async replication → MySQL read replicas → Slightly stale, much faster reads Minutes–Hours → Analytics dashboards, reports → Batch ETL pipelines → Data warehouse (Redshift, BigQuery) → Very stale ok, extremely cheap CAP Theorem implication: → Choose Consistency: payments, bookings (CP system) → Choose Availability: social feeds, likes (AP system)
22
Data Growth Rate — Future-proofing your architecture
Design for 3× your current load. Plan sharding before you need it.
Future QPS = current QPS × growth_rate ^ years
Growth rate benchmarks: Hypergrowth startup = 3× per year Growing product = 1.5–2× per year Mature product = 1.1–1.3× per year Example — startup at 1,000 QPS today: Year 1: 1,000 × 3 = 3,000 QPS Year 2: 3,000 × 3 = 9,000 QPS Year 3: 9,000 × 3 = 27,000 QPS → Plan sharding now, even if you don't need it today → Much harder to shard a live production DB
23
Throughput vs Latency Trade-off
Batching increases throughput but adds latency. Choose based on SLA.
Kafka batching example: Batch size 1 → 1,000 msg/sec throughput, 5ms latency Batch size 100 → 50,000 msg/sec throughput, 50ms latency Batch size 1000 → 200,000 msg/sec throughput, 500ms latency Decision framework: Use small batches (low latency): → Real-time notifications, chat messages, payments Use large batches (high throughput): → Analytics events, logs, metrics, bulk imports Little's Law — relates throughput, concurrency, latency: Concurrency = Throughput × Latency If throughput doubles and latency stays same → need 2× servers

Availability & Reliability

Availability SLAs drive replica count, failover strategy, and backup frequency. Always state your target — interviewers expect this.

SLADowntime/YearDowntime/MonthDowntime/WeekArchitecture implication
99% 3.65 days7.3 hours1.68 hours Single server, manual recovery ok
99.9% 8.7 hours43 min10 min Load balancer + 2 servers, basic failover
99.99% 52 min4.4 min1 min Multi-AZ, auto-failover, <1 min recovery — FAANG target
99.999% 5.2 min26 sec6 sec Multi-region active-active, zero manual intervention
MTTR / MTBF — Recovery time calculations: MTTR = Mean Time To Recovery (how long to fix a failure) MTBF = Mean Time Between Failures (how often it breaks) Availability = MTBF ÷ (MTBF + MTTR) To achieve 99.99%: Target MTTR = under 1 minute Requires = automated failover (not human paging someone) Solution = multi-AZ deployment, health checks, auto-scaling Replica count for durability: Replication factor 1 → data lost if server dies (never do this) Replication factor 2 → survives 1 failure (minimum) Replication factor 3 → survives 2 simultaneous failures (standard) Kafka, Cassandra, HDFS all default to RF=3
💡
Compound availability: If service A is 99.9% and service B is 99.9%, together they're only 99.9% × 99.9% = 99.8%. Every dependency you add reduces your availability. This is why microservices need circuit breakers (Hystrix, Resilience4j).

Thundering Herd Problem

The most common cache-related production incident. When your cache expires, all requests simultaneously slam your DB. This is what takes down systems at scale.

The problem — Normal operation: Read QPS = 10,000 Cache hit rate = 95% DB load = 10,000 × 5% = 500 QPS → DB fine The problem — Cache cold start (server restart, mass expiry): Read QPS = 10,000 Cache hit rate = 0% (cache just came back empty) DB load = 10,000 × 100% = 10,000 QPS → DB DIES
Solution 1 — TTL Jitter (easiest)
base_ttl = 300 seconds jitter = random(-60, +60) actual_ttl = base_ttl + jitter → Cache entries expire at random times → No thundering herd at expiry ★ Always do this
Solution 2 — Mutex / Cache Lock
if cache_miss: if acquire_lock("rebuild:key"): result = query_db() cache_set(key, result) release_lock() else: wait_and_retry() # others wait → Only ONE request rebuilds cache → All others wait, then read cache
Solution 3 — Stale While Revalidate
if cache_expired: serve stale data immediately async: refresh_cache_in_background() → User never waits for cache rebuild → Sees slightly stale data for seconds → Used by most CDNs and browsers
Solution 4 — Cache Warming
on_server_start(): pre_load_top_1000_items_into_cache() then_open_traffic() on_cache_near_expiry(): proactively_refresh() # before it expires → Cache is never cold → Requires predicting what to warm
🔥
Real-world impact: This has taken down Amazon, Facebook, and almost every company at scale. If you mention thundering herd + at least one solution in an interview, you immediately signal senior-level thinking. Most candidates at junior/mid level have never heard of it.

The Universal Framework

Use this exact sequence for every BOTE question. Never skip a step. Talk out loud at every step — interviewers want to hear your thinking.

1
Clarify & State Assumptions
Before calculating anything, state what you're assuming. "I'll assume 500M registered users with 20% DAU, so 100M daily active users." Interviewers can correct you here — they want you to ask questions, not just calculate.
Ask: scale? read-heavy or write-heavy? global or single region? any spiky events?
2
Establish Users (DAU/MAU)
Total users → DAU. Everything else multiplies off this number. A 10× error here cascades everywhere.
DAU = total × active_rate (10–20% consumer, 50%+ messaging, 5% B2B)
3
Define Actions — Reads AND Writes Separately
How many times does each DAU read and write per day? Be specific. "10 feed refreshes" and "1 post" are different numbers with different implications.
writes/day = DAU × writes/user | reads/day = DAU × reads/user
4
Size Per Item — List Every Field
Don't say "about 1KB". List each field with its byte count. Sum them. Add 30% for fields you forgot. This discipline separates strong candidates from weak ones.
total bytes = Σ(field sizes) × 1.3
5
Calculate Daily Numbers
Simple multiplication. writes/day × bytes/item = storage/day. reads/day stays separate.
storage/day = writes/day × bytes | reads/day = DAU × reads/user
6
Convert to Per Second (QPS)
Divide by 100,000 (rounded 1 day). Now you have numbers you can compare against infrastructure limits.
QPS = daily count ÷ 100,000
7
Scale Out — Peak and Long-Term
Multiply QPS by 3 for peak. Multiply storage by 365×5 for 5-year planning. Multiply by 3 for replication factor. These are the numbers that define your infrastructure.
peak QPS = avg × 3 | storage 5yr = /day × 1,825 | actual disk = logical × 3
8
Conclude — Connect Every Number to a Decision
Never leave a number floating. Every single number must connect to a specific technology or architecture decision. This is what separates system design from arithmetic.
Number → Bottleneck → Technology choice → Justification

BookMyShow — Ticket Booking

Normal vs Flash Sale Traffic
Normal day: 5M DAU × 5 views = 25M/day ÷ 100K = 250 QPS Flash sale (Coldplay drops tickets): 1M users all click buy in 10 seconds Peak QPS = 1,000,000 ÷ 10 = 100,000 QPS Peak = 400× normal → normal infra collapses completely
Seat Inventory in Cache
Venue: 50,000 seats seat_id=8 | status=1 | price=8 | version=4 → 50 bytes/seat 50,000 × 50 = 2.5 MB total inventory → Entire inventory fits in Redis 1000× over → All seat reads served from Redis, DB only for final write
Virtual Queue Math
1M users wanting 50K seats: 95% of users will get rejected → design for graceful rejection Queue position = user enters queue, gets a number Only top 60K (50K seats + 20% buffer) get to checkout page → Reduces DB pressure from 1M concurrent to 60K → Redis ZADD for sorted queue by join_time
DB Connection Pool Warning
At 100K QPS even from queue: App servers = 20 (scaled up for flash sale) Threads each = 50 DB connections = 20 × 50 = 1,000 connections Postgres default = 100 → instant 500 errors Solution: PgBouncer connection pooler

Common Mistakes — What Kills Your Interview

Leaving numbers floating without a conclusion
❌ "We'll have 10,000 read QPS."
✓ "10,000 read QPS exceeds MySQL's ~5K QPS limit, so we need a Redis cache layer and read replicas to protect the DB."
Every number must connect to a specific architecture decision. Numbers without conclusions are just arithmetic — not system design.
Forgetting the replication factor (3×)
❌ "We need 900 TB of storage."
✓ "900 TB logical storage × replication factor 3 = 2.7 PB actual disk to purchase."
Every byte in a distributed system is stored 3 times. Forgetting this makes your capacity plan 3× too small.
Ignoring media — it always dominates by 100–1000×
❌ Calculating only text storage and stopping there.
✓ Always ask: "Does this system have images or video?" Twitter text = 2.5 GB/day. Twitter media = 500 GB/day. Media is 200× larger.
On any social or content platform, media always dominates storage, bandwidth, and cost decisions.
Using total registered users instead of DAU
❌ "Twitter has 500M users so 500M requests per day."
✓ "500M registered × 20% daily active = 100M DAU. Size infrastructure for active users, not accounts created in 2009."
Guessing object sizes instead of listing fields
❌ "A tweet is about 1 KB I think."
✓ List: tweet_id(8) + user_id(8) + text(300) + timestamp(8) + counts(8) = 332 bytes → round to 500.
The discipline of field-level estimation signals rigorous thinking. Guessing signals you're not systematic.
Not accounting for peak traffic (3× average)
❌ Sizing servers for average load only.
✓ "Average is 10K QPS, peak is 30K QPS. I'll size for 30K. BookMyShow sees 400× at flash sales."
Systems that work at average load and die at peak are production outages waiting to happen.
Forgetting DB connection pool exhaustion
❌ Designing 50 app servers, never checking if DB can accept 50×50=2,500 connections.
✓ "Postgres default is 100 connections. 50 servers × 50 threads = 2,500 needed. Must add PgBouncer."
This causes mysterious 500 errors in production and nobody knows why. Mentioning it signals real-world experience.
Ignoring the thundering herd on cache expiry
❌ Adding a cache and thinking the problem is solved.
✓ "When cache expires, 10K QPS hits the DB simultaneously. Must add TTL jitter + stale-while-revalidate."
Not asking about consistency requirements before designing
❌ Jumping straight to adding read replicas for everything.
✓ "First: is eventual consistency ok for this use case? Payments: no → sync replication. Feed: yes → async replicas."
Consistency requirements completely change your DB choice. Ask first, then design.
Never mentioning cost or business constraints
❌ Designing an infinitely scalable system with no regard for cost.
✓ "Without CDN our egress is $23K/month. With CDN it drops to $1,150/month. CDN is clearly worth it."
Senior engineers think about cost. Mentioning even rough cost estimates signals real-world awareness.
