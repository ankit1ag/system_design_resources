Chapter 01

Recursion

A function that calls itself. Sounds simple. Changes everything.

"To understand recursion, you must first understand recursion." — Every CS professor ever

The One Mental Model You Need

Every recursive problem is a tree of function calls. Each node is one function call. Each branch is a recursive call. The leaves are your base cases.

If you can draw this tree for any problem, you've solved it.

// fibonacci(4) — the call tree
                    fib(4)
                   /        \
              fib(3)         fib(2)
             /     \        /     \
          fib(2)  fib(1)  fib(1)  fib(0)
          /    \
       fib(1)  fib(0)

Each node = one function call
Each leaf = base case (returns immediately)
Answer = combine results coming back UP the tree

The 3 Laws of Recursion (Memorize These)

1

BASE CASE — The Exit Door

Every recursion MUST have a condition where it stops calling itself. Without this, you get a stack overflow. Always write this first.

Rule
Ask: "What's the smallest version of this problem I can answer directly without recursing?" Empty array → 0. n=0 → 1. Single char → true. That's your base case.
2

RECURSIVE CASE — Make the Problem Smaller

Each recursive call must move toward the base case. Usually: solve for n → call for n-1, or left half / right half, or shrink the array.

Rule
Ask: "If I had the answer for a SMALLER version of this problem, could I solve the current version?" If yes → recurse. This is called the Inductive Hypothesis.
3

TRUST THE RECURSION

Don't try to mentally simulate the full tree. Assume your recursive call works correctly for smaller input, then just use its result. This is the hardest mental shift.

Aditya Verma's Advice
"Mere function ko pata nahi ki andar kya ho raha hai. Main sirf trust karta hoon ki chota problem solve ho gaya." (I don't care what happens inside. I trust the smaller problem is solved.)

The Universal Recursion Template (Java)

Every single recursive function follows this exact structure:

JAVA returnType solve(params) { // 1. BASE CASE — stop recursing if (baseCondition) { return baseValue; } // 2. RECURSIVE CASE — smaller problem // Choice: what am I deciding at this step? returnType smaller = solve(smallerParams); // 3. COMBINE — use smaller result to build current return combine(smaller, currentDecision); }

Two Styles: Print vs Return (Critical Distinction)

Print Approach

Work is done before the recursive call. Things happen on the way DOWN the tree.

void print(int[] arr, int i) { if (i == arr.length) return; // base System.out.println(arr[i]); // PRINT first print(arr, i+1); // then recurse } // Output: 1 2 3 4 5 (forward)

Return Approach

Work is done after the recursive call returns. Things happen on the way UP the tree.

void printReverse(int[] arr, int i) { if (i == arr.length) return; // base printReverse(arr, i+1); // recurse first System.out.println(arr[i]); // PRINT after } // Output: 5 4 3 2 1 (reverse!)
The Secret
Before the recursive call = going down the tree (pre-order).
After the recursive call = coming back up (post-order).
This is WHY tree traversal preorder/inorder/postorder is literally just where you put the print statement!

Recursion Variations — Complete Map

Linear Recursion

One call per level. Stack depth = n.

// Factorial int fact(int n) { if(n==0) return 1; return n * fact(n-1); }

Time: O(n) · Space: O(n) stack

Binary Recursion (Tree-shaped)

Two calls per level. Stack grows as tree. 2ⁿ nodes.

// Fibonacci (naive) int fib(int n) { if(n<=1) return n; return fib(n-1) + fib(n-2); }

Time: O(2ⁿ) · Space: O(n) stack

Tail Recursion

Recursive call is the LAST operation. Can be optimized to a loop. Java doesn't auto-optimize but concept matters.

// Tail-recursive factorial int factTail(int n, int acc) { if(n==0) return acc; return factTail(n-1, n*acc); // last op }

Mutual Recursion

A calls B, B calls A. Rare but appears in parsing, game theory.

boolean isEven(int n) { if(n==0) return true; return isOdd(n-1); } boolean isOdd(int n) { if(n==0) return false; return isEven(n-1); }

Classic Recursion Problems (Build in This Order)

1

Factorial / Fibonacci

Learn the pattern. Fibonacci shows why naive recursion is O(2ⁿ) — you solve the same subproblem repeatedly. This is the seed of DP.

2

Array: Sum, Reverse, Sorted Check

Practice making arrays smaller: solve for arr[0..n-1] using result of arr[0..n-2].

3

String: Palindrome, Permutations, Subsequences

Two choices at each step: include or exclude current character. This gives you 2ⁿ leaves. This is the seed of Backtracking.

4

Towers of Hanoi

The best problem to understand "trust the recursion." You CANNOT solve it without trusting sub-calls work. Crucial mindset shift.

void hanoi(int n, char from, char aux, char to) { if(n==1) { System.out.println("Move disk 1 from "+from+" to "+to); return; } hanoi(n-1, from, to, aux); // trust: move n-1 to aux System.out.println("Move disk "+n+" from "+from+" to "+to); hanoi(n-1, aux, from, to); // trust: move n-1 to dest }
Chapter 02

Backtracking

Recursion with an undo button.

"Backtracking is just recursion where you explore all choices — and erase your footprints when a path doesn't work." — The definition that actually makes sense

What IS Backtracking?

Backtracking = Recursion + State Restoration.

You make a choice → recurse deeper → if it leads to a dead end or you've found an answer → undo the choice → try the next option.

Recursion → explore a path
Backtracking → recursion + undo when path fails
The Key Mental Model
Think of it as navigating a maze:
• You walk down a corridor (make a choice)
• If it's a dead end → you walk back to the last junction (undo)
• Try the next corridor
• Repeat until you find the exit (answer) or exhaust all paths

The Universal Backtracking Template

This is Aditya Verma's exact framework. Learn it once, apply it forever.

JAVA — MASTER TEMPLATE void backtrack(State current, List result, ...) { // ① BASE CASE — did we reach a valid complete solution? if (isComplete(current)) { result.add(new copy(current)); // COPY! not reference! return; } // ② LOOP through all possible choices at this step for (Choice choice : getAllChoices(current)) { // ③ CHOOSE — make the choice, modify state makeChoice(current, choice); // ④ EXPLORE — recurse with new state backtrack(current, result, ...); // ⑤ UNCHOOSE — undo the choice (this is the "back" in backtrack) undoChoice(current, choice); } }
The Crucial Insight
Steps ③ and ⑤ are always mirrors of each other. If you add to a list → remove from list. If you set grid[r][c]=true → set it back to false. If you swap → swap back. Always symmetric.

Problem 1: Subsets (The Foundation of ALL Backtracking)

Generate all subsets of [1,2,3]. This single problem teaches you the entire decision tree model.

// Decision tree for [1, 2, 3]
                         []
                    /          \
               [1]              []           ← include 1 OR not
              /    \          /    \
           [1,2]  [1]      [2]     []        ← include 2 OR not
           / \    / \      / \    / \
        [1,2,3][1,2][1,3][1] [2,3][2][3][]  ← include 3 OR not

All 8 (2³) leaves = all subsets. Each internal node = one decision.
JAVA void subsets(int[] nums, int start, List<Integer> curr, List<List> result) { // Every node in the tree is a valid subset (not just leaves) result.add(new ArrayList(curr)); // ← COPY current state for (int i = start; i < nums.length; i++) { curr.add(nums[i]); // ③ CHOOSE: include nums[i] subsets(nums, i+1, curr, result); // ④ EXPLORE curr.remove(curr.size()-1); // ⑤ UNCHOOSE: remove last } } // Call: subsets(nums, 0, new ArrayList(), result)

Problem 2: Permutations

Unlike subsets, order matters. At each step you can pick ANY unused element.

JAVA void permute(int[] nums, boolean[] used, List<Integer> curr, List<List> result) { if (curr.size() == nums.length) { // base: picked all result.add(new ArrayList(curr)); return; } for (int i = 0; i < nums.length; i++) { if (used[i]) continue; // skip already used used[i] = true; // ③ CHOOSE curr.add(nums[i]); permute(nums, used, curr, result); // ④ EXPLORE curr.remove(curr.size()-1); // ⑤ UNCHOOSE used[i] = false; } }

Pruning: The Superpower of Backtracking

Without pruning, backtracking = brute force. Pruning cuts entire branches of the decision tree early.

Pruning = "Don't explore paths that CAN'T lead to a solution"

In Combination Sum: if current sum > target, stop. Don't recurse further.
In N-Queens: if column/diagonal is attacked, skip that placement.
In Sudoku: if digit violates rules, try next digit.

JAVA — Combination Sum with PRUNING void combinationSum(int[] candidates, int target, int start, List<Integer> curr, List<List> res) { if (target == 0) { res.add(new ArrayList(curr)); return; } if (target < 0) return; // ✂ PRUNE: overshot, abandon branch for (int i = start; i < candidates.length; i++) { // ✂ PRUNE: sorted array — no point going further if (candidates[i] > target) break; curr.add(candidates[i]); combinationSum(candidates, target - candidates[i], i, curr, res); curr.remove(curr.size()-1); } }

All Backtracking Problem Types

Enumeration

Generate all valid configurations. Collect ALL leaves.

→ Subsets, Permutations, Combinations, String permutations

Constraint Satisfaction

Find ONE valid configuration satisfying constraints.

→ N-Queens, Sudoku, Word Search, Graph Coloring

Optimization

Among all valid configurations, find the BEST one.

→ 0/1 Knapsack (brute), Rat in Maze, Subset with min sum

When Optimization Backtracking meets Overlapping Subproblems
That's exactly when you should switch to Dynamic Programming. If you find yourself solving the same subproblem multiple times in your backtracking tree → memoize → DP.
Chapter 03

Dynamic Programming

Recursion that remembers what it's already done.

"DP is just recursion with a cache, or table-filling that avoids redundant work. There's no magic — only memory." — Aditya Verma's foundational principle

The Origin Story of DP

Look at Fibonacci with naive recursion:

                      fib(5)
                    /        \
               fib(4)         fib(3)
              /      \       /      \
          fib(3)   fib(2) fib(2)  fib(1)
          /    \
       fib(2) fib(1)

fib(3) computed TWICE. fib(2) computed THREE TIMES. fib(1) four times.
For fib(50) this becomes 2^50 calls. Total waste.

DP Solution: Store the result of fib(n) the FIRST time. Reuse it.
DP = Recursion + Memoization (Top-Down) OR Tabulation (Bottom-Up)
Both compute the same answers. Memoization is natural recursion + HashMap cache. Tabulation is filling a table from smallest to largest subproblem.

DP Works ONLY When Both Conditions Hold

1. Optimal Substructure

The optimal answer to the big problem can be constructed from optimal answers to subproblems.

Test: "Can I break this into smaller same-shaped problems?"

fib(n) = fib(n-1) + fib(n-2) ✓
Shortest path: built from shortest sub-paths ✓

2. Overlapping Subproblems

The same subproblem appears multiple times in the recursion tree.

Test: "Is my recursion tree solving the same node multiple times?"

fib(3) appears 2x in fib(5) ✓
If all subproblems unique → just use D&C, not DP ✗

Two Styles: Top-Down (Memoization) vs Bottom-Up (Tabulation)

Top-Down (Memoization)

= Recursion + Cache

Start from the big problem. Recurse down. Before returning, store result in map. Next time same subproblem hits → return from cache.

Map<Integer,Integer> memo = new HashMap(); int fib(int n) { if(n <= 1) return n; if(memo.containsKey(n)) return memo.get(n); // HIT! int res = fib(n-1) + fib(n-2); memo.put(n, res); // STORE return res; }

Pros: Natural to write. Only computes needed subproblems.
Cons: Recursion stack overhead. Stack overflow risk for large n.

Bottom-Up (Tabulation)

= Iterative table filling

Start from the smallest subproblems. Fill the table up to the answer. No recursion needed.

int fib(int n) { if(n<=1) return n; int[] dp = new int[n+1]; dp[0]=0; dp[1]=1; // base cases for(int i=2; i<=n; i++) dp[i] = dp[i-1] + dp[i-2]; return dp[n]; } // Space optimize: only need last 2! int a=0, b=1; for(int i=2;i<=n;i++){int c=a+b;a=b;b=c;}

Pros: No recursion. No stack overflow. Easier to space-optimize.
Cons: Must figure out fill order. May compute unneeded subproblems.

Aditya Verma's 5-Step DP Recipe (Never Forget)

This is taken directly from his Knapsack playlist. Apply to EVERY DP problem.

1

Write the Recursive Solution First

Don't think about DP yet. Just write clean recursion. Identify what changes in each call — these are your variables.

// For 0/1 Knapsack — what changes each call?
→ current item index (n)
→ remaining weight capacity (W)
→ These become your dp table dimensions: dp[n][W]
2

Identify Overlapping Subproblems

Draw the recursion tree. Do you see the same (n, W) pair computed twice? If yes → memoize it. The variables that repeat = your cache keys.

3

Add Memoization (Top-Down)

Add a HashMap or 2D array. Before recursing, check if result is cached. After computing, store it.

// 3 lines added to any recursion to make it memoized: int[][] dp = new int[n+1][W+1]; // at start of function: if(dp[n][W] != 0) return dp[n][W]; // before returning: return dp[n][W] = result;
4

Convert to Bottom-Up (Tabulation)

Look at your recursive calls' base cases → these are your table initialization. Look at recursion direction → that's your loop order.

The Conversion Rule
Top-down: solve(n, W) calls solve(n-1, W) and solve(n-1, W-wt)
Bottom-up: fill dp[i][j] using dp[i-1][j] and dp[i-1][j-wt[i]]
The recurrence is the SAME. Only execution order differs.
5

Space Optimization

If dp[i][j] only depends on dp[i-1][j] → you only need 2 rows or even 1 row (iterate correctly).

// 2D dp[n][W] → 1D dp[W] // Key: iterate W from right to left for 0/1 Knapsack! for(int i=1; i<=n; i++) { for(int j=W; j>=wt[i]; j--) { // ← RIGHT TO LEFT dp[j] = Math.max(dp[j], val[i]+dp[j-wt[i]]); } }

The Knapsack Family (Root of Most DP Problems)

Aditya Verma's insight: almost every DP problem is a variant of Knapsack. Learn the root, derive the variants.

JAVA — 0/1 KNAPSACK (The Root) // Recursive with memoization int knapsack(int[] wt, int[] val, int W, int n, int[][] dp) { if(n == 0 || W == 0) return 0; // base case if(dp[n][W] != -1) return dp[n][W]; // cache hit if(wt[n-1] <= W) { // Choice 1: INCLUDE item n int include = val[n-1] + knapsack(wt, val, W-wt[n-1], n-1, dp); // Choice 2: EXCLUDE item n int exclude = knapsack(wt, val, W, n-1, dp); return dp[n][W] = Math.max(include, exclude); } else { return dp[n][W] = knapsack(wt, val, W, n-1, dp); // must exclude } }

Subset Sum

Can we pick items to make sum = target?

Same as Knapsack but val=1, target=capacity. Returns boolean.

→ Partition Equal Subset Sum

Count of Subsets

How many subsets have sum = target?

Add counts instead of max. dp[i][j] += dp[i-1][j] + dp[i-1][j-nums[i]]

→ Count Subsets with Target, Perfect Sum

Min Subset Diff

Partition into two subsets minimizing |S1-S2|.

Find all achievable sums ≤ total/2. Answer = min(total - 2*s).

→ Partition with Minimum Difference

Unbounded Knapsack

Items can be used unlimited times.

Change: after including item n, DON'T decrement n. Stay at same item.

→ Coin Change, Rod Cutting

Coin Change

Min coins to make amount. Unbounded knapsack variant.

dp[i] = min coins for amount i. dp[0]=0, dp[i]=min(dp[i-coin]+1)

→ Coin Change I, II

Target Sum

Assign +/- to each num, count ways to reach target.

Reduce to: count subsets with sum = (total+target)/2. Pure Knapsack.

→ Target Sum (LC 494)

The LCS Family

Longest Common Subsequence is the second root of string DP problems.

JAVA — LCS (The Root) int lcs(String s1, String s2, int m, int n) { if(m==0 || n==0) return 0; // base if(s1.charAt(m-1) == s2.charAt(n-1)) return 1 + lcs(s1, s2, m-1, n-1); // match! take both else return Math.max(lcs(s1,s2,m-1,n), // skip s1[m] lcs(s1,s2,m,n-1)); // skip s2[n] }

From LCS → These Problems

  • Longest Common Substring
  • Shortest Common Supersequence
  • Min Insertions/Deletions to Convert
  • Print LCS

Related String DP (different roots)

  • Edit Distance (insert/delete/replace)
  • Palindromic Subsequence (LCS of s and reverse(s))
  • Distinct Subsequences
  • Wildcard / Regex Matching
Chapter 04

The Connection

They're not three different topics. They're one topic at different zoom levels.

RECURSION the foundation — build a decision tree

↓ add state restoration

BACKTRACKING recursion + undo — explore ALL branches

↓ cache repeated subproblems

DYNAMIC PROGRAMMING backtracking + memory — never recompute
All three are the same tree. You just decide: explore everything (BT), or remember and skip (DP).

The Progression: Same Problem, Three Approaches

Let's solve Fibonacci three ways to see the exact evolution:

R

Pure Recursion — O(2ⁿ) — Correct but Slow

int fib(int n) { if(n<=1) return n; return fib(n-1) + fib(n-2); // solves same subproblem 2^n times }

The recursion tree has exponential nodes. fib(3) recomputed many times. ❌ TLE on big inputs.

M

Memoization (Top-Down DP) — O(n) — Same tree, cache added

Map<Integer,Integer> cache = new HashMap(); int fib(int n) { if(n<=1) return n; if(cache.containsKey(n)) return cache.get(n); // skip recomputation int res = fib(n-1) + fib(n-2); return cache.put(n, res); // store before returning }

Same recursion. 3 lines changed. Exponential → linear. This is literally the only difference.

T

Tabulation (Bottom-Up DP) — O(n) time O(1) space

int fib(int n) { int a=0, b=1; for(int i=2; i<=n; i++) { int c = a+b; a=b; b=c; } return b; }

No recursion. Fill from bottom up. Two variables because only last 2 matter.

When to Use Which — The Decision Flowchart

SIGNAL IN PROBLEM USE WHY
Simple decomposition, no repeated work Recursion No need for cache. D&C problems (merge sort, binary search).
"Generate ALL solutions" / "find any valid" Backtracking Must explore all paths. Pruning makes it fast enough.
Counting problems ("how many ways") DP Counting requires summing over subproblems. Overlap guaranteed.
Optimization ("max/min value") DP Optimal substructure + overlap = DP territory.
Constraint satisfaction (valid config) Backtracking Must verify constraints at each step. No easy recurrence.
Subset/combination existence DP (Knapsack variant) dp[i][j] = can we achieve sum j with first i items?
String transformation (edit distance) 2D DP dp[i][j] = answer for s1[0..i] and s2[0..j]
Permutations / arrangements Backtracking Order matters. Must track what's been used. No recurrence.

The Key Insight: DP Can't Do Everything BT Does

Backtracking CAN do these, DP CANNOT
  • Print/collect ALL solutions
  • Problems with complex state (position + orientation + ...)
  • Constraint satisfaction where constraints span multiple variables (N-Queens, Sudoku)
  • When you need to UNDO state (graph coloring)
DP CAN do these, BT is too slow
  • Count number of solutions (TLE with BT)
  • Find minimum/maximum over all solutions
  • n ≥ 100 (BT is exponential, DP is polynomial)
  • When answer doesn't need to be reconstructed

The Exact Framework (Applied to Every Problem)

Aditya's playlist solves every problem in this exact order. Memorize the sequence:

①

Identify the Variables That Change

Look at your recursive function. Which parameters change with each call? These are your DP state variables.

Knapsack: n (current item), W (remaining capacity) → dp[n][W]
LCS: m (s1 index), n (s2 index) → dp[m][n]
Climbing Stairs: n (current stair) → dp[n]
Stock: day, holding, transactions → dp[day][hold][k]
②

Write Pure Recursion (Ignore Efficiency)

Don't think about time complexity. Write the cleanest, most obvious recursive solution. This becomes your DP foundation.

Aditya's Trick for Base Cases
Base case = when one of the changing variables hits 0 or its boundary. n=0 means no items left. W=0 means no capacity. m=0 or n=0 means one string exhausted.
③

Memoize: Add Cache (2 Lines)

// Before the recursive call: if (dp[n][W] != -1) return dp[n][W]; // Change every return statement to: return dp[n][W] = (your expression);

Initialize dp with -1. That's it. Recursion → memoized DP done.

④

Tabulate: Flip to Bottom-Up

Look at your memoized solution. Base cases → table initialization. Recursion direction → loop direction.

// Memoized: solve(n, W) calls solve(n-1, W) // Table: dp[i][j] uses dp[i-1][j] // So: outer loop i from 1 to n, inner j from 0 to W for(int i=0; i<=n; i++) dp[i][0]=0; // base: W=0 for(int j=0; j<=W; j++) dp[0][j]=0; // base: n=0 for(int i=1; i<=n; i++) { for(int j=1; j<=W; j++) { if(wt[i-1] <= j) dp[i][j] = Math.max(val[i-1]+dp[i-1][j-wt[i-1]], dp[i-1][j]); else dp[i][j] = dp[i-1][j]; } }
⑤

Space Optimize (Interview Flex)

The Direction Rule
0/1 Knapsack: iterate j from W down to 0 (right to left) — prevents using same item twice.
Unbounded Knapsack: iterate j from 0 to W (left to right) — allows reuse.

The "Never Forget" Summary Card

RECURSION
USE WHEN Problem naturally breaks into smaller same-shaped problems. No repeated subproblems.

REMEMBER ① Base case
② Smaller call
③ Trust + combine
BACKTRACKING
USE WHEN Need all solutions. Constraints checked per step. State must be restored.

REMEMBER ① Choose
② Explore
③ Unchoose (mirror)
DP
USE WHEN Optimal substructure + overlapping subproblems. Count or optimize.

REMEMBER ① Recursive solution
② ID variables
③ Memoize
④ Tabulate
⑤ Space optimize
